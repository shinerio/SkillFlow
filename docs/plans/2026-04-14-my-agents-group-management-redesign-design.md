# 我的智能体全局分组与启停管理重构设计

**日期：** 2026-04-14

## 背景

当前“我的智能体”已经具备以下能力：

- 左侧按智能体切换
- `全部` 视图查看聚合 skill
- 单智能体视图查看推送路径、扫描路径与记忆
- 单 skill 和整组启停的后端能力

但现有交互存在明显问题：

1. `新建分组` 使用浏览器原生 `window.prompt`，在桌面壳中缺少稳定反馈，用户会感觉按钮无响应。
2. `全部` 视图使用列表式管理，不符合“我的技能”里已经建立的“侧边栏 + 卡片网格 + 拖拽归类”交互心智。
3. 单智能体下的 skill 启停管理与来源浏览混在一个页面里，信息密度高但操作效率低。
4. 当前启停管理使用纵向条目，不适合大量 skill 的快速扫描和批量操作。

本次设计的目标不是重做数据模型，而是在保持现有全局分组与每智能体启停语义不变的前提下，重构“我的智能体”交互层。

## 已确认约束

1. 分组是全局共享的。
2. 分组按 `skillName` 归属，而不是按智能体隔离。
3. `全部` 视图负责全局分组管理。
4. 单个智能体视图负责当前智能体的 skill 来源浏览与启停管理。
5. 单个智能体中需要新增清晰入口进入 enable / disable 管理面板。
6. skill 管理界面应使用多行多列卡片布局。
7. 分组管理交互参考“我的技能”的体验，采用侧边栏 + 卡片拖拽。

## 备选方案

### 方案 A：最小修补

- 把 `window.prompt` 换成应用内弹窗
- 保留当前列表式 `全部` 视图
- 把单智能体启停条目改成卡片

优点：

- 改动小
- 风险低

缺点：

- 交互仍与“我的技能”割裂
- 分组体验依旧弱
- 用户需要同时理解两套不同的管理模式

### 方案 B：局部重构，对齐“我的技能”

- `全部` 视图改成左侧分组侧边栏 + 右侧卡片网格
- 支持把 skill 卡片拖拽到分组
- 单智能体 skill 页保留来源浏览，但新增“启停管理”模式
- 启停管理视图采用卡片网格，并按启用状态分区

优点：

- 与“我的技能”交互一致
- 保留现有后端模型，改动集中在前端
- 信息架构更清晰

缺点：

- 需要重排 `ToolSkills` 页面结构
- 需要补充一批前端状态与交互测试

### 方案 C：提取通用分组框架

- 把“我的技能”的分类面板、卡片拖拽、卡片动作全部抽成通用框架
- “我的智能体”完全复用

优点：

- 长期结构最统一

缺点：

- 本次任务范围明显扩大
- 容易把已有页面也卷入重构

## 选型

采用 **方案 B：局部重构，对齐“我的技能”**。

原因：

- 它满足本次用户目标，且不引入额外后端复杂度。
- 它复用现有全局分组语义，不需要改动持久化结构。
- 它能直接修复当前“新建分组无反馈”和“启停管理不直观”两个核心问题。

## 信息架构

### 1. `全部` 视图

`全部` 视图只负责全局分组管理，不承担单智能体启停。

布局：

- 左侧：分组侧边栏
- 右侧：skill 卡片网格

左侧结构：

- `全部`
- `未分组`
- 所有自定义分组

右侧卡片显示：

- skill 名称
- 当前分组
- 出现在哪些智能体
- 实例数

交互：

- 点击侧边栏筛选当前分组
- 拖拽 skill 卡片到某个分组完成归类
- 拖拽到 `未分组` 等价于清空分组
- 新建、重命名、删除分组使用应用内弹窗和菜单，不再使用原生 prompt

### 2. 单智能体视图

单智能体仍保留：

- `技能`
- `记忆`

其中 `技能` 页签拆分为两个运行模式：

- 默认模式：来源浏览
- 管理模式：启停管理

默认模式职责：

- 展示推送路径中的 skill 卡片
- 展示扫描路径中的 skill 卡片
- 保留现有手动拉取、批量删除、只读扫描卡片等能力

管理模式职责：

- 展示当前智能体下所有可管理 skill
- 提供单 skill 与整组的启用 / 停用操作
- 使用卡片网格，而不是纵向列表

入口：

- 在单智能体 `技能` 页签头部新增 `启停管理` 按钮
- 点击后切换到管理面板
- 管理面板支持返回来源浏览视图

## 状态模型

本次不修改后端领域模型，仅调整前端组织方式。

继续沿用：

- 全局分组：`skillName -> groupName`
- 每智能体禁用状态：
  - `disabledSkillNames`
  - `disabledGroupNames`

前端视图语义：

- `未分组` 是展示层概念
- 真实持久化仍然通过“没有 assignment”表达未分组

## 关键交互设计

### 1. 新建 / 重命名 / 删除分组

统一采用应用内交互：

- 新建分组：打开弹窗
- 重命名分组：打开预填名称的弹窗
- 删除分组：打开确认弹窗

校验规则：

- 空名称不可提交
- 纯空格不可提交
- 与已有分组重名不可提交
- 提交中按钮禁用
- 出错时在弹窗内展示错误

### 2. 分组拖拽

参考“我的技能”的拖拽模式：

- 右侧卡片可拖动
- 左侧分组是 drop target
- 拖拽悬停时高亮目标分组
- 放下后调用后端，再刷新数据

采用保守刷新策略：

- 不做复杂乐观更新
- 成功后重新加载

原因：

- 当前分组变化会影响 `全部` 与单智能体多个视图
- 保守刷新更容易保持一致性

### 3. 启停管理视图

管理视图使用卡片网格，分为两个区块：

- 已启用
- 已禁用

每张卡片显示：

- skill 名称
- 所属分组
- 路径数量
- 启用状态
- 单 skill 操作按钮

每个分组头显示：

- 分组名
- skill 数量
- 整组启用 / 停用按钮

特殊提示：

- Codex 继续显示“修改后需重启生效”

## 视图构建规则

### `全部` 页侧边栏来源

侧边栏分组列表由两部分合并：

- 配置中的 `groupNames`
- 当前 skill 数据中实际出现的 `groupName`

这样可以避免下面这种情况：

- 某个 skill 已经有分组
- 但因为配置列表未同步，侧边栏不显示该分组

### 单智能体管理视图分区

管理视图先按启用状态切两区，再在区内按分组聚合。

这样做的好处是：

- 用户最关心的是“现在哪些被关了”
- 分区比单纯全局按组排列更容易发现异常状态

## 错误处理

1. 分组操作失败：
   - 弹窗内显示错误
   - 保持当前输入，不清空
2. 拖拽归类失败：
   - 保持当前页面状态
   - 显示轻量错误提示
3. 启停失败：
   - 对应卡片或组头按钮进入 loading 后恢复
   - 显示错误提示
4. 空状态：
   - `全部` 页无 skill：显示引导文案
   - 分组为空：显示“拖拽技能到这里进行分组”
   - 启停分区为空：显示“暂无已启用技能”或“暂无已禁用技能”

## 非目标

本次不做以下内容：

1. 分组按智能体隔离
2. skill 多分组归属
3. 复杂乐观更新
4. 抽离一整套跨页面通用分组框架
5. 改变后端持久化结构

## 结论

本次重构采用“全局分组管理”和“单智能体启停管理”分离的方式：

- `全部` 做全局分组
- 单智能体 `技能` 做来源浏览与启停管理

这样既能复用现有后端能力，又能把交互体验对齐到“我的技能”的成熟模式，并直接修复“新建分组无响应”和“管理入口不清晰”的问题。
